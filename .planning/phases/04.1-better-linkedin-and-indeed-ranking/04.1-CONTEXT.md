# Phase 4.1: Better LinkedIn and Indeed Ranking - Context

**Gathered:** 2026-11-12
**Status:** Ready for planning

<domain>
## Phase Boundary

LinkedIn and Indeed alert jobs (and any other job with only a short snippet) are ranked on more than a title. The details worker looks each one up once on the Reed API and, on a confident title + company match, copies Reed's full description in. The person can paste a description through the API, which always wins. Jobs that still have only a snippet are scored fairly and labelled "partial info". Alert jobs whose links carry no job ID are deduplicated by title and company.

LinkedIn and Indeed are still never contacted (Phase 4 D-18). Out of this phase: employer careers / ATS lookups and Adzuna (see Deferred), the UI paste box itself (UI pages come after this roadmap; this phase ships the API endpoint), autofill (Phase 5) and the Apply queue (Phase 6).

</domain>

<decisions>
## Implementation Decisions

### Where to look for the job
- **D-01:** The only lookup source is the **Reed API**, using the existing Reed key setting and `sources.py` Reed client patterns. No employer careers pages, no ATS feeds, no Adzuna. With no Reed key saved, the lookup is skipped quietly (Phase 2 D-09).
- **D-02:** The lookup runs **inside the existing details worker** (Phase 4 D-11). LinkedIn and Indeed jobs, which `core.details_plan` currently marks `skipped`, become Reed-lookup candidates instead, processed one at a time with the same 5 s gap. Existing jobs already marked `skipped` are covered too. No new thread.
- **D-03:** **One try, then stop.** A job with no Reed match (or no key at the time) is not retried; it stays "open listing to read" and keeps the paste option.

### Match rules and what a match changes
- **D-04:** A Reed result matches only when the **company is the same** after normalising (case, punctuation, and suffixes such as Ltd, Limited, plc, LLP, Group removed) **and the title is near-identical** (`difflib` ratio ≥ 0.9 on `core.normalise`d titles). Location is only a tie-breaker between several matching results, never a requirement. No match on company → no match.
- **D-05:** On a match: copy Reed's **full description** into the alert job; fill **salary and job type only where the alert left them empty**; **keep the alert's own URL** as the job's URL; record that the description came from Reed (e.g. a pro/note "Description from Reed"); re-summarise and re-score **only if the job is still `new`** (Phase 4 D-13). The Reed link itself is not stored.
- **D-06:** A **pasted description always wins**: it replaces whatever description is there (snippet or Reed's) and the job is marked as pasted so a later automatic lookup never overwrites it. — **Reversibility:** costly — the way a job is marked "pasted" (a new `details_status` value or another field) becomes part of the job shape the future UI reads; pick one representation and keep it.
- **D-07:** A paste **re-scores the job whatever its status** (new, queued or dismissed), because it is a deliberate act by the person. Automatic Reed matches keep the new-only rule. This is a deliberate exception to Phase 1 D-08 / Phase 3 D-09 / Phase 4 D-13, for pastes only.
- **D-08:** The paste is an **API endpoint** (the UI paste box comes later). Shape is at Claude's discretion; it must validate input (non-empty text, a sensible maximum length), store plain text only (`core.plain_text`, Phase 4 T-04-12), return 404 for an unknown job, and go through the existing `local_only` guard.

### Scoring partial info
- **D-09:** A job is **partial info** when its description is shorter than 500 characters (`core.SHORT_DESCRIPTION_CHARS`) **and** it was not filled from Reed or by a paste. This applies to any source, not only LinkedIn and Indeed.
- **D-10:** For partial-info jobs the skills rule gives a **neutral credit**: still count profile skills found in the title and snippet, but award at least **half of `SKILL_POINTS_CAP`**, so a job with a strong title, salary or work-mode match is not buried for lacking text. Once a full description arrives (Reed or paste), the real skills count replaces the credit.
- **D-11:** **"Salary not listed" stays a con** for partial-info jobs (it costs no points today, so nothing changes).
- **D-12:** Partial info shows as a **con with a next step**, worded like "Only the alert snippet — paste the description for a full score", **plus a flag in the job's `summary`** that the future UI can show as a badge.

### Claude's Discretion
- **Duplicate merging (not discussed; planner decides):** suggested default — merge only among alert-sourced jobs whose links carry no job ID (indeed-match, totaljobs-invite, sponsored Indeed `pagead/clk`), on normalised title + normalised company (same normalisation as D-04), keeping the **older row and its status** and dropping the newcomer. Cross-source merging (an alert job vs the same Reed job) is optional; if done, it must never change a queued/dismissed row's status.
- The exact Reed API calls (search parameters, whether the full description needs a per-job details call), result limits per lookup, and how the lookup result is recorded in `details_status`.
- The paste endpoint path and response shape.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `api/sources.py` `fetch_reed` / `REED_URL` / `get_json`: Reed client with basic-auth key, `SourceError` on failure — reuse for the lookup search.
- `api/core.py` `details_plan`: currently returns `skipped` for LinkedIn/Indeed (`NEVER_FETCH_SOURCES`); the branch to change for D-02.
- `api/core.py` `normalise`, `matched_skills`, `SHORT_DESCRIPTION_CHARS`, `SKILL_POINTS_CAP`, `score`: the scoring rules D-09..D-12 extend.
- `api/db.py` `save_details`, `next_pending`: description save + new-only re-score path (extend for Reed match; add a paste path that re-scores any status).
- `api/watcher.py` `_details_step` / `_details_loop`: the worker the lookup plugs into.
- `difflib` (stdlib): already used for answer matching (Phase 3 D-10).

### Established Patterns
- Re-score only `new` jobs (`AND status = 'new'` on the score UPDATE) — keep for automatic matches, bypass only for pastes.
- `details_status` values today: `pending`, `ok`, `blocked`, `skipped`.
- Flask routes return `{"error": ...}` with 4xx; all `/api/` routes behind `local_only`.
- Tests are plain `api/test_*.py` scripts printing `ok: N tests`; network faked by swapping `sources.get_json` / `sources.get_page`.

### Integration Points
- Details worker → Reed lookup → `save_details`-style write.
- New paste endpoint in `api/app.py` → db write → re-score.
- `core.score` / `core.summarize` → partial-info flag and con.
- `db.insert_jobs` (dedupe currently `UNIQUE(url)` only) → title+company merge for ID-less alert links.

</code_context>
