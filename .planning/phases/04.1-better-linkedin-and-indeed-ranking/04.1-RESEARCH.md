## User Constraints (from CONTEXT.md)

### Locked Decisions

**Where to look for the job**
- **D-01:** The only lookup source is the **Reed API**, using the existing Reed key setting and `sources.py` Reed client patterns. No employer careers pages, no ATS feeds, no Adzuna. With no Reed key saved, the lookup is skipped quietly (Phase 2 D-09).
- **D-02:** The lookup runs **inside the existing details worker** (Phase 4 D-11). LinkedIn and Indeed jobs, which `core.details_plan` currently marks `skipped`, become Reed-lookup candidates instead, processed one at a time with the same 5 s gap. Existing jobs already marked `skipped` are covered too. No new thread.
- **D-03:** **One try, then stop.** A job with no Reed match (or no key at the time) is not retried; it stays "open listing to read" and keeps the paste option.

**Match rules and what a match changes**
- **D-04:** A Reed result matches only when the **company is the same** after normalising (case, punctuation, and suffixes such as Ltd, Limited, plc, LLP, Group removed) **and the title is near-identical** (`difflib` ratio >= 0.9 on `core.normalise`d titles). Location is only a tie-breaker between several matching results, never a requirement. No match on company -> no match.
- **D-05:** On a match: copy Reed's **full description** into the alert job; fill **salary and job type only where the alert left them empty**; **keep the alert's own URL** as the job's URL; record that the description came from Reed (e.g. a pro/note "Description from Reed"); re-summarise and re-score **only if the job is still `new`** (Phase 4 D-13). The Reed link itself is not stored.
- **D-06:** A **pasted description always wins**: it replaces whatever description is there (snippet or Reed's) and the job is marked as pasted so a later automatic lookup never overwrites it. - **Reversibility:** costly - the way a job is marked "pasted" (a new `details_status` value or another field) becomes part of the job shape the future UI reads; pick one representation and keep it.
- **D-07:** A paste **re-scores the job whatever its status** (new, queued or dismissed), because it is a deliberate act by the person. Automatic Reed matches keep the new-only rule. This is a deliberate exception to Phase 1 D-08 / Phase 3 D-09 / Phase 4 D-13, for pastes only.
- **D-08:** The paste is an **API endpoint** (the UI paste box comes later). Shape is at Claude's discretion; it must validate input (non-empty text, a sensible maximum length), store plain text only (`core.plain_text`, Phase 4 T-04-12), return 404 for an unknown job, and go through the existing `local_only` guard.

**Scoring partial info**
- **D-09:** A job is **partial info** when its description is shorter than 500 characters (`core.SHORT_DESCRIPTION_CHARS`) **and** it was not filled from Reed or by a paste. This applies to any source, not only LinkedIn and Indeed.
- **D-10:** For partial-info jobs the skills rule gives a **neutral credit**: still count profile skills found in the title and snippet, but award at least **half of `SKILL_POINTS_CAP`**, so a job with a strong title, salary or work-mode match is not buried for lacking text. Once a full description arrives (Reed or paste), the real skills count replaces the credit.
- **D-11:** **"Salary not listed" stays a con** for partial-info jobs (it costs no points today, so nothing changes).
- **D-12:** Partial info shows as a **con with a next step**, worded like "Only the alert snippet - paste the description for a full score", **plus a flag in the job's `summary`** that the future UI can show as a badge.

## Summary

The phase is almost entirely wiring on top of Phase 4. The details worker already decides per job (`core.details_plan`) and writes through `db.save_details`; this phase adds a fourth plan value (`"lookup"`) for LinkedIn/Indeed jobs, a Reed lookup function in `sources.py` that reuses the existing basic-auth header and `get_json`, two new `details_status` values (`reed`, `pasted`), one paste endpoint, a pure `is_partial` predicate feeding `score()`, and a `dedupe_key` column with a partial unique index for ID-less alert links.

The Reed search endpoint returns only a short preview in `jobDescription`; the full text needs one extra call per job to `/api/1.0/jobs/{jobId}` [CITED: jobspipe.dev/blog/reed-api, and Phase 2 research]. So the lookup is: 1 search (up to 2 query variants) to find a candidate, local company+title match, then 1 details call only for the single matched candidate. That keeps the cost at 1-3 requests per job, which matters because a third-party source states a 1000 requests/day limit per key [CITED: publicapi.dev/reed-api, MEDIUM] and the existing backlog of LinkedIn/Indeed rows (29 Indeed jobs in one sample email alone) is processed once at the next start.

Three design points are non-obvious and decide whether this works: (1) the Reed pro, the paste pro, the partial con and the partial flag must be **derived inside `score()` / `job_dict` from `details_status` and description length**, not appended once at save time, because `rescore_new` rebuilds pros/cons from scratch on every settings or profile save; (2) a paste must win a race against an in-flight worker fetch, so every worker write needs a `details_status != 'pasted'` guard in its SQL; (3) the title ratio of 0.9 alone accepts "Software Engineer" vs "Software Engineer II" (measured 0.919), so add a level-word guard.

**Primary recommendation:** Add `core.is_partial / company_key / reed_match / dedupe_key`, `sources.reed_lookup`, `db.save_reed_match / paste_description`, a `PUT /api/jobs/<id>/description` route, and a `dedupe_key` column; derive every user-visible partial/Reed/paste string in `score()` from `details_status`; keep `reed` and `pasted` as the two new `details_status` values; verify the Reed details field names with one real-key call before the final plan closes.

### Pattern 1: Derive, don't append (scoring text from state)
**What:** `score()` reads `job.get("details_status")` and the description length and emits the partial con, the Reed pro, the paste pro and the skills credit itself.
**When to use:** every user-visible string whose truth depends on `details_status`.
**Why:** `db.rescore_new` rebuilds `pros`/`cons` from scratch for every `new` row on any settings or profile save (`api/db.py:191-198`); a string appended only at save time would vanish.
**Example (skeleton; constants verbatim from the repo and UI-SPEC):**
```python
# core.py
MAX_DESCRIPTION_CHARS = 20000
PARTIAL_CON = "Only the alert snippet — paste the description for a full score"   # UI-SPEC binding

def is_partial(job: dict) -> bool:
    """D-09: short text, and not filled from Reed or pasted."""
    return (job.get("details_status") not in ("reed", "pasted")
            and len(plain_text(job.get("description") or "")) < SHORT_DESCRIPTION_CHARS)

# in score(), replacing the skills block:
partial = is_partial(job)
profile_skills = (profile or {}).get("skills") or []
hits = matched_skills(profile_skills, job)
pts = min(SKILL_POINTS_EACH * len(hits), SKILL_POINTS_CAP)
if partial and profile_skills:                       # D-10 neutral credit; see Open Question 3 on the profile_skills gate
    pts = max(pts, SKILL_POINTS_CAP // 2)
total += pts
if hits:
    pros.append("Matches %d of your skills: ..." )   # unchanged text
# ... after the excluded-words block:
if job.get("details_status") == "reed":   pros.append("Description from Reed")
if job.get("details_status") == "pasted": pros.append("Description pasted by you")
if partial: cons.append(PARTIAL_CON)
```
`SKILL_POINTS_CAP // 2` is 5 [VERIFIED: `SKILL_POINTS_CAP = 10  # below TITLE_POINTS, so salary stays the heaviest rule`, api/core.py:258].

### Pattern 2: Flag computed on read
**What:** `db.job_dict` sets `d["summary"]["partial_info"] = core.is_partial(d)` after the JSON decode.
**Why:** D-05 says an automatic Reed match re-scores only `new` jobs, so a queued job's stored summary/pros/cons go stale by design. Computing the flag at read time keeps `summary.partial_info` true to the UI-SPEC ("false as soon as filled from Reed or pasted") for *every* status with no extra write. The stale `cons` line on a queued job is the accepted D-13 freeze (scores freeze when queued); note it in the plan so a verifier does not flag it. Call sites covered automatically: `list_jobs`, `get_job`, `set_status`, `rescore_new` (via `job_dict`), and the paste response.

### Pattern 3: One transactional write, guarded in SQL
**What:** Worker writes (`save_details`, `save_reed_match`) add `AND details_status != 'pasted'` to the UPDATE that sets the description, and run the re-score UPDATE only if that UPDATE touched a row (`cur.rowcount == 1`).
**Why:** the worker reads the row, spends seconds on the network, then writes; a paste committed in between would otherwise be overwritten (violates D-06). The existing `AND status = 'new'` clause on the score UPDATE (`api/db.py:226`) is the same idea for D-13; keep it for Reed matches, **omit** it for `paste_description` (D-07).

### Pattern 4: Skeletons for the new db functions
```python
# db.py (shape only; reuse the hint-preservation lines from save_details)
DETAILS_STATUSES = ("pending", "ok", "blocked", "skipped", "reed", "pasted")
# save_details keeps `DETAILS_STATUSES[1:]` check, so restrict the worker-allowed set there explicitly
# (reed/pasted are written only by their own functions): WORKER_STATUSES = ("ok", "blocked", "skipped")

def _rescored(conn, row, text, status, salary=None, job_type=None):
    old = json.loads(row["summary"])                       # source hints are not columns; keep them (Phase 4 Pitfall 3)
    job = dict(job_dict(row), description=text, details_status=status,
               salary=row["salary"] or salary or "",
               job_type=old.get("job_type") or job_type, remote=old.get("remote"))
    summary = core.summarize(job)
    total, pros, cons = core.score(dict(job, summary=summary), get_settings(conn), get_profile(conn))
    return job["salary"], summary, total, pros, cons

def paste_description(conn, job_id, text):              # text already plain_text'ed and validated by the caller
    with conn:
        row = conn.execute("SELECT * FROM jobs WHERE id = ?", (job_id,)).fetchone()
        if row is None: raise KeyError(job_id)
        salary, summary, total, pros, cons = _rescored(conn, row, text, "pasted")
        conn.execute("UPDATE jobs SET description=?, details_status='pasted', summary=?, score=?, pros=?, cons=? WHERE id=?",
                     (text, json.dumps(summary), total, json.dumps(pros), json.dumps(cons), job_id))   # no status condition: D-07
        return job_dict(conn.execute("SELECT * FROM jobs WHERE id = ?", (job_id,)).fetchone())
```
`save_reed_match` is the same with `details_status='reed'`, the extra `salary` column write, `WHERE id=? AND details_status != 'pasted'` on the description UPDATE, and `AND status='new'` on the score UPDATE. When the lookup finds nothing it calls the existing `save_details(conn, id, "", "blocked")`.

**Salary column write:** for a non-`new` job the `salary` column and description are still written (D-05 "fill salary and job type only where empty") but summary/score are not recomputed; the summary's `salary_*` fields therefore stay stale for queued rows (accepted, same as the stale score).

### Pattern 5: Idempotent migration in `init_db`
```python
# after the existing details_status ALTER, inside init_db (idempotent, runs every start)
if "dedupe_key" not in [r[1] for r in conn.execute("PRAGMA table_info(jobs)")]:
    with conn: conn.execute("ALTER TABLE jobs ADD COLUMN dedupe_key TEXT")
with conn:
    conn.execute("CREATE UNIQUE INDEX IF NOT EXISTS jobs_dedupe_key ON jobs(dedupe_key) WHERE dedupe_key IS NOT NULL")
    # D-02 "existing jobs already marked skipped are covered": only the D-18 skips, never the excluded-word skips
    conn.execute("UPDATE jobs SET details_status = 'pending' WHERE details_status = 'skipped' AND source IN ('linkedin', 'indeed')")
```
A partial unique index plus `INSERT OR IGNORE` was exercised this session: with rows `(a,x) (b,x) (c,NULL) (d,NULL)` the inserts returned rowcount `1 0 1 1`, so the second `x` is ignored and NULL keys never collide [VERIFIED: sqlite3 run, SQLite 3.51.0].

Re-pending `skipped` LinkedIn/Indeed rows each start also re-pends any that were skipped for an excluded word; `details_plan` checks excluded words first and re-skips them with no network, so this is harmless churn (one cheap pass per start). After a lookup a row is `reed`, `pasted` or `blocked`, never `skipped`, so the UPDATE does not loop. Existing tests that assert LinkedIn/Indeed end `skipped` must change (see Validation).

### Pattern 7: Reed lookup function
```python
# sources.py
REED_JOB_URL = "https://www.reed.co.uk/api/1.0/jobs/%d"

def _reed_auth(api_key):    # extracted from fetch_reed, behaviour unchanged
    return {"Authorization": "Basic " + base64.b64encode((api_key + ":").encode()).decode()}

def reed_lookup(job, api_key):
    """{"text", "salary", "job_type"} for the Reed ad that is this job, or None. Raises SourceError on failure."""
    auth = _reed_auth(api_key)
    title, company = job.get("title") or "", job.get("company") or ""
    try:
        best = None
        for kw in dict.fromkeys(["%s %s" % (title, company), title]):        # at most 2 searches
            results = get_json(REED_URL, {"keywords": kw, "resultsToTake": 100}, headers=auth)["results"]
            best = core.reed_match(job, results)
            if best: break
        if not best: return None
        d = get_json(REED_JOB_URL % int(best["jobId"]), {}, headers=auth)   # int(): never interpolate API text into a path
        text = core.plain_text(d.get("jobDescription") or "")
        if not text: return None
        kind = " ".join(str(d.get(k) or "") for k in ("jobType", "contractType"))   # key names ASSUMED, see A1
        return {"text": text, "salary": _salary_text(d.get("minimumSalary"), d.get("maximumSalary")),
                "job_type": core._first_label(core.normalise(kind), core._TYPES)}
    except (OSError, ValueError, KeyError, TypeError, AttributeError) as e:
        raise SourceError("Reed lookup failed: %s" % e)        # message from the exception only: never params/headers/url
```
`resultsToTake` default and maximum is 100 [CITED: reed.co.uk/developers/jobseeker]. `get_json` appends `"?" + urlencode(params)`, so `{}` yields a trailing `?` which Reed ignores [ASSUMED harmless; covered by the real-key check].

### Pattern 8: Match rules (pure, in `core`)
```python
_COMPANY_NOISE = _LEGAL | {"group", "the", "and"}          # D-04 lists Ltd, Limited, plc, LLP, Group; "and" fixes "Marks & Spencer" vs "Marks and Spencer"
_LEVEL = {"junior", "senior", "lead", "principal", "head", "graduate", "trainee", "intern", "assistant", "associate",
          "i", "ii", "iii", "iv", "1", "2", "3", "4"}      # ponytail: fixed list; a level word that differs = a different job

def company_key(name):
    words = normalise(name).split()
    return " ".join([w for w in words if w not in _COMPANY_NOISE] or words)      # same empty-fallback as answer_block_reason

def reed_match(job, results):
    """Best Reed result for this alert job, or None. D-04: same company AND title ratio >= 0.9; location only breaks ties."""
    ck, nt = company_key(job.get("company")), normalise(job.get("title"))
    if not ck or not nt: return None                      # no company -> no match
    where = set(normalise(job.get("location")).split())
    best, best_key = None, None
    for r in results:
        rt = normalise(r.get("jobTitle"))
        if company_key(r.get("employerName")) != ck: continue
        ratio = _ratio(nt, rt)
        if ratio < 0.9 or (set(nt.split()) ^ set(rt.split())) & _LEVEL: continue
        key = (len(where & set(normalise(r.get("locationName")).split())), ratio)
        if best_key is None or key > best_key: best, best_key = r, key
    return best
```
Measured ratios on `core.normalise`d titles [VERIFIED: ran `core._ratio` this session]: "Senior Data Analyst" vs "Data Analyst" = 0.774 (rejected), "Data Analyst" vs "Data Analyst (Remote)" = 0.774 (rejected), "Python Developer" vs "Python Developer - London" = 0.821 (rejected), "Data Analyst" vs "Data Analysts" = 0.96 (accepted), **"Software Engineer" vs "Software Engineer II" = 0.919 (accepted by ratio alone, hence the `_LEVEL` guard)**. Expect a modest hit rate: real Indeed alert titles carry reference numbers and suffixes (sample: "Inclusion Co-ordinator and Designated Safeguarding Lead (DSL) (7817)") that will not reach 0.9 against Reed's title. That is the intended strictness.

`normalise` turns `&` and `-` into spaces: "Marks & Spencer plc" -> `marks spencer plc`, "Co-op Group Ltd" -> `co op group ltd` [VERIFIED: ran `core.normalise`]. So "Co-op Group Ltd" -> key `op` after `co`, `group`, `ltd` are stripped; both sides get the same treatment so equality still holds, but note `co` is in `_LEGAL` and is stripped from any position.

### Pattern 9: Dedupe for ID-less alert links
- `alerts.alert_job(..., idless=False)`: `if idless: job["dedupe"] = True` (key added only when True so `test_alert_job_shape`'s `set(job) == {...}` assertion at `api/test_gmail.py:578` still holds).
- Pass `idless=True` from `parse_indeed_match`, `parse_totaljobs_invite`, and from `parse_indeed` when the link path starts with `/pagead/clk` (re-derive from the url with `urlsplit(url).path.startswith("/pagead/clk")`).
- `core.dedupe_key(title, company)` -> `None` when company is empty (title-only keys would merge unrelated jobs), else `normalise(title) + "|" + company_key(company)`.
- `db.insert_jobs`: add `dedupe_key` to the INSERT column list, value `core.dedupe_key(...) if job.get("dedupe") else None`. The existing `INSERT OR IGNORE` then drops the newcomer on a key clash and keeps the older row with its status; `new` is only incremented when `rowcount == 1`.
- Real samples show why: `indeed-match` URL is `https://cts.indeed.com/v3/REDACTED/REDACTED` and `totaljobs-invite` is `https://web.totaljobsmail.co.uk/o-REDACTED` (opaque tracker paths), so URL dedupe cannot catch repeats [VERIFIED: parsed `api/samples/*.eml` this session].
- Not backfilled: rows inserted before this phase keep `dedupe_key NULL` (pre-existing duplicates stay; YAGNI). Cross-source (Reed vs alert) merging is skipped; add a `# ponytail:` note next to the existing one at `api/sources.py:114`.
- Ceiling to document: identical title+company at different locations (a chain posting the same role in five towns) merge into one row. The decision keys on title+company only; location is deliberately not in the key (see Open Question 4).

### Pattern 10: The paste route
```python
# app.py  (PUT = replace semantics; sits beside the existing /api/jobs/<id>/cover-letter route)
@app.put("/api/jobs/<int:job_id>/description")
def job_description(job_id):
    body = request.get_json(silent=True)
    raw = body.get("description") if isinstance(body, dict) else None
    if not isinstance(raw, str) or not raw.strip():
        return jsonify(error="Paste the job description first"), 400
    if len(raw) > core.MAX_DESCRIPTION_CHARS:
        return jsonify(error="That description is too long. Keep it under %d characters." % core.MAX_DESCRIPTION_CHARS), 400
    text = core.plain_text(raw)
    if not text:                                          # e.g. only tags
        return jsonify(error="Paste the job description first"), 400
    try:
        return jsonify(db.paste_description(get_db(), job_id, text))
    except KeyError:
        return jsonify(error="Job not found. It may have been removed from the list."), 404
```
Order is body validation (400) first, then existence (404), the same order as `answers_put`. Reject at `len(raw) > MAX` on the raw string *before* `plain_text`, so text is never silently truncated. The response is the full `job_dict`, so the future UI can refresh score, pros, cons and `summary.partial_info` from it (UI-SPEC interaction rule 2). `get_json(silent=True)` already parses the whole body; Flask has no `MAX_CONTENT_LENGTH` here by design (`app.py:22` comment), and the endpoint is local-only, so a body cap is optional (`# ponytail:`).

### Anti-Patterns to Avoid
- **Appending the Reed/paste pro or the partial con in `save_*`:** wiped by the next `rescore_new`. Derive in `score()`.
- **Gating "partial" on `source in (linkedin, indeed)`:** D-09 says any source.
- **Blindly flipping every `skipped` row to `pending`:** `skipped` also means excluded-word title (Phase 4 D-12). Restrict the migration to `source IN ('linkedin','indeed')`; `details_plan` re-skips excluded titles.
- **Fetching the alert URL or the Reed `jobUrl` for LinkedIn/Indeed jobs:** D-18. `reed_lookup` must only ever call `reed.co.uk` API URLs; it must not use `fetch_details`/`get_page`.
- **Storing Reed's `jobUrl`:** D-05 says it is not stored; do not copy `url`.
- **Re-scoring queued/dismissed rows on an automatic match:** only `new` (D-05/D-13). Only `paste_description` is exempt (D-07).
- **Adding a pro in `save_reed_match` only when the score changes:** the pro is derived from `details_status == 'reed'`, independent of the new-only rule (a queued row's stored pros stay as they were, accepted).

## Common Pitfalls

### Pitfall 1: Derived strings lost on rescore
**What goes wrong:** the Reed pro / partial con disappears after the person saves a setting.
**Why:** `rescore_new` recomputes pros/cons from scratch.
**How to avoid:** derive in `score()` from `details_status` and length (Pattern 1). **Warning signs:** a test that saves settings after a Reed match and still expects "Description from Reed".

### Pitfall 2: Paste overwritten by an in-flight worker
**What goes wrong:** the worker fetched a page/Reed ad while the person pasted; its later `save_details`/`save_reed_match` replaces the paste.
**How to avoid:** `details_status != 'pasted'` in the UPDATE's WHERE, gate the second UPDATE on `rowcount` (Pattern 3). Test with a fake `get_json` that performs the paste mid-lookup.

### Pitfall 3: `skipped` is overloaded
**What goes wrong:** the migration or the new plan order sends excluded-word LinkedIn jobs to Reed.
**How to avoid:** excluded-word check stays first in `details_plan`; migration only touches D-18 rows, and the worker re-skips excluded ones with no network.

### Pitfall 4: Title ratio accepts a level change
**What goes wrong:** "Software Engineer" matches "Software Engineer II" (0.919) and the wrong ad's text is copied in, which is worse than no text.
**How to avoid:** `_LEVEL` symmetric-difference guard (Pattern 8). Only narrows D-04, so it is within its "only when" wording.

### Pitfall 5: `plain_text` eats comparison operators in a paste
**What goes wrong:** pasted plain text `salary <£50k and >£30k` becomes `salary £30k` because `_TAG` removes `<...>` spans [VERIFIED: ran `core.plain_text("salary <£50k and >£30k, 3 <years")` -> `salary £30k, 3 <years`].
**Why it matters:** D-08 mandates `core.plain_text`, so keep it; it is an edge case in a deliberate paste. Mention it in the plan's known ceilings (`# ponytail:` comment on the route); do not add a second sanitiser.

### Pitfall 6: Test fakes route on host substring
**What goes wrong:** `api/test_watcher.py` `fake_get_json` returns `{"results": REED_ITEMS}` for *any* URL containing `reed.co.uk`, which includes the new `/api/1.0/jobs/<id>` URL, and raises `AssertionError` for unknown hosts [VERIFIED: api/test_watcher.py:34-44]. A details-worker test that runs with a Reed key and a LinkedIn row would hit this.
**How to avoid:** put the lookup tests in `test_details.py` with their own `sources.get_json` fake that dispatches on the path (`/search` vs `/jobs/`), and restore the original in `finally`. Keep `test_watcher.py` unchanged unless a lookup row is created there.

### Pitfall 7: Reed quota
**What goes wrong:** the first start after deploy re-pends every old LinkedIn/Indeed row; at 2 searches + 1 details each, a few hundred rows can approach a 1000/day limit [CITED: publicapi.dev/reed-api, third party; treat as undocumented per Reed's own page, which names no limit].
**How to avoid:** at most 2 searches + 1 details per job; `next_pending` already orders by `score DESC`, so the best jobs are looked up first; a 429 ends that job as `blocked` (D-03), so the quota cannot cause a retry storm. Do not add back-off.

### Pitfall 8: A short non-alert description is also "partial"
**What goes wrong:** a Reed-sourced job whose page fetch returned 200-499 characters (accepted by `BLOCKED_TEXT_CHARS = 200`) is `partial_info: true` and carries the "alert snippet" con (D-09 is literal: not filled from Reed or pasted).
**How to avoid:** accept, it is rare; the wording is UI-SPEC-binding. See Open Question 2.

### Pitfall 9: Python 3.9 vs 3.12
**What goes wrong:** using `str | None` or `list[str]` annotations breaks on 3.9. **How to avoid:** use `typing.Optional`/`List` as the existing files do.

def details_plan(job, settings):
    """No-network decision: "skipped", "ok" (already long enough), "lookup" (Reed, LinkedIn/Indeed) or "fetch"."""

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Stored XSS via pasted or Reed text | Tampering | `core.plain_text` before write; the UI renders text only (UI-SPEC rule 6); residual note from 04-SECURITY (decoded `&lt;` may reappear as `<`) stays open for the UI phase |
| Cross-site / DNS-rebinding call to the paste route | Spoofing | `local_only` guard (existing) |
| Path injection through an API-supplied job id | Tampering | `int(best["jobId"])` before `%d` formatting |
| Reed key leakage in errors or logs | Information Disclosure | Messages from the exception only (same rule as `fetch_reed`); no `repr` of requests |
| Compliance: contacting LinkedIn/Indeed | Compliance | Plan value `lookup` makes no page request; test asserts no LinkedIn/Indeed URL ever reaches `get_json`/`get_page`/browser |
| Oversized paste (DoS) | Denial of Service | 20000-char cap checked on the raw string; `plain_text` regexes are bounded; local-only caller |
| Wrong ad copied in (integrity) | Tampering | Strict company equality + title ratio + level guard; no match -> nothing copied |
