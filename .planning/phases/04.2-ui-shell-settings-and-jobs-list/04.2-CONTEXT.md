# Phase 4.2: UI Shell, Settings and Jobs List - Context

**Gathered:** 2026-11-13
**Status:** Ready for planning

<domain>
## Phase Boundary

The first real browser UI, built on the existing API only (no backend changes beyond what tests need): the app shell with top nav and pushState routing, the full design-token set, the Settings page (career fields, excluded words, minimum salary, location, Reed key, poll intervals, Gmail connect/disconnect, per-source watcher status, Check now), and the Jobs **list** view (JobCard, PartialInfoBadge + PasteDescription per 04.1, filter chips + title search, optimistic dismiss/queue with Undo toast, new-jobs pill, tab-title unread count), with loading/empty/error states. The look, wording, states and interactions are locked by `04.2-UI-SPEC.md`; this file locks *how* it is built and checked.

Out of scope: swipe view and `motion` (Phase 4.3), Dashboard, Profile page, Apply queue page, `Start.bat`/packaging (UI-05, v2 milestone).

</domain>

<decisions>
## Implementation Decisions

### Routing and packages
- **D-01:** Routing is a small hand-written `history.pushState` router (a `useRoute`-style hook, `<a>` click interception, `popstate`), for the five fixed URLs in the UI-SPEC (`/`, `/queue`, `/dashboard`, `/profile`, `/settings`) plus the 404. No `react-router-dom`. Flask's existing `index.html` fallback serves deep links.
- **D-02:** `motion` is **not** installed in this phase. The list-row collapse and toast use plain CSS transitions (respecting `prefers-reduced-motion`). `motion` arrives with the swipe deck in Phase 4.3.
- **D-03:** Any new npm package follows the backend rule: exact version pin, committed lockfile, and a short legitimacy check (publisher, downloads, repository) before install; a blocking human checkpoint when the package is new to the project. With D-01, D-02 and D-04 this phase should need **no** new runtime packages.

### How UI work is tested
- **D-04:** The main automated check is Node's built-in test runner (`node --test`, Node 22 here, run on `.ts` via type stripping) over pure logic modules. No Vitest, no Testing Library. `tsc`, `oxlint` and `npm run build` cover the rest. `npm test` in `ui/package.json` runs it.
- **D-05:** Testable logic lives in `ui/src/lib/*.ts` with colocated `*.test.ts` (e.g. `lib/filters.ts` + `lib/filters.test.ts`): filter matching (chips OR, search AND), poll diffing for the new-jobs pill, tab-title/unread count, API error-message extraction (`{"error"}` body vs network failure wording), relative-time wording. Components stay thin and import from `lib/`.
- **D-06:** One end-to-end smoke test in Python Playwright, `api/test_ui_smoke.py` (reuses the existing `playwright` dependency; this Mac needs `playwright install chromium` once — no browser is downloaded yet). It starts Flask on a temp DB (`JOBHELPER_DB`, the pattern in `api/test_api.py`) with seeded jobs, serves the freshly built UI, and checks: nav between pages, saving a setting, dismiss + undo of a job, **keyboard-only** dismiss + undo with the focus targets the UI-SPEC names, and **no horizontal scroll** (`document.scrollWidth ≤ innerWidth`) on Jobs and Settings at 320px and 1280px widths. No axe-core.
- **D-07:** Tests talk to the **real Flask app on a temp DB**, never mocked fetch, so they cannot drift from the API.
- **D-08:** The smoke test is a phase-end gate, not a per-task check: it runs at the end of each plan that changes a page and before the human check. Per-task verification is `npm test` + `tsc` + `npm run lint` + `npm run build` (plus backend tests when anything in `api/` changes).

### Shipping the built UI
- **D-09:** `api/static/` stays gitignored. This phase builds locally for development and for the smoke test only; how the bundle reaches the Windows PC is decided by UI-05 packaging (v2). — **Reversibility:** reversible — a later packaging step can choose to commit or zip the build.

### End-of-phase human check
- **D-10:** The phase closes with a blocking human-verification checkpoint done by the developer on this Mac: built UI served by Flask at `http://localhost:8765`, desktop browser plus a 320px devtools width, light and dark mode. The Windows PC check waits for UI-05.
- **D-11:** The check runs on **seeded test data first** (scripted, repeatable steps: Settings save, Gmail connected/disconnected state, Check now, filters, dismiss/queue/undo, paste description, keyboard-only pass, 320px), **then a quick look at the developer's real DB** (real Reed and Gmail jobs: long titles, partial-info jobs, real errors).

### Claude's Discretion
- Plan slicing and wave order (tracer-first by default), exact `lib/` module boundaries, the shape of the `usePoll` hook and `api.ts` helpers within the UI-SPEC and UI-MAP contracts, how the smoke test seeds jobs and starts/stops Flask.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `ui/src/index.css`: five tokens (`--bg --text --muted --ok --bad`) and dark mode via `prefers-color-scheme`; the UI-SPEC token block extends this `:root`.
- `ui/vite.config.ts`: dev proxy `/api` → `:8765`, build to `../api/static` — no change needed.
- `api/app.py` `ui()` route: serves built files and falls back to `index.html` for client routes (D-01 depends on it).
- `api/test_api.py`: temp-DB pattern via `JOBHELPER_DB` + `tempfile` — reuse for the smoke test (D-06, D-07).

### Established Patterns
- Backend tests are plain-`assert` Python scripts run directly (`.venv/bin/python api/test_*.py`); the UI tests mirror that plainness with `node --test`.
- API errors are always `{"error": "..."}` with a 4xx/5xx status and user-facing wording — the UI shows them as-is.
- Ponytail style (CLAUDE.md): stdlib/native before deps, no unrequested abstractions, `ponytail:` comments on deliberate shortcuts.

### Integration Points
- Endpoints used: `GET/PUT /api/settings`, `GET /api/watcher`, `POST /api/fetch`, `GET/PUT/DELETE /api/gmail`, `GET /api/jobs?status=new`, `POST /api/jobs/<id>/dismiss|queue|undo`, `PUT /api/jobs/<id>/description`.
- `PUT /api/jobs/<id>/description` comes from Phase 4.1 plan 03, which must be finished before this phase executes.
- `ui/src/App.tsx` (health-check stub) and `ui/src/main.tsx` are replaced/extended.

</code_context>

## Specific Ideas

- Keep the UI dependency-free beyond React for this phase: router, polling, transitions and tests all use the platform or stdlib.
- The smoke test's two layout widths (320 and 1280) and the keyboard path mirror the UI-SPEC's Accessibility and Layout sections, so a failure points straight at a spec line.
